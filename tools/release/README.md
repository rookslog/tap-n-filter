# Tagged release automation

`release.yml` admits only `vX.Y.Z`, `vX.Y.Z-alpha.N` and `vX.Y.Z-beta.N` tags at exact commits reachable from protected `main`. It checks both local ancestry and current GitHub tag/main identity. Tag text enters Python through environment variables, never shell source. Existing macOS 15 and 26 runners build the exact commit with latest-stable Xcode, `swift build` and default `swift test` in release configuration with two jobs. Native engine, device, audio and window tests remain opt-in and disabled. Neither the app nor its probe/engine tools are launched.

Only the executable, its complete nested SwiftPM resource bundle, the app icon and source Info.plist enter the ad-hoc-signed app. No test bundles, helper executables, data or local audit files are copied. The normal library branch needs no external helper; owned probe tooling is not part of this package. Signature, architecture and resource correspondence checks run before imaging and again on the app read from the attached disk image. No Developer ID lookup, signing-account access or notarization occurs. Ad-hoc signing is not notarization and does not remove Gatekeeper requirements.

The marketing version matches X.Y.Z. To support zero-major versions with a positive Apple build component, the bundle build version maps X.Y.Z to `(X+1).Y.Z`, with `aN` for alphas and `bN` for betas. Components must fit four/two/two digits and the alpha or beta N is 1 through 255. The DMG and provenance filenames contain the full tag, runner and observed architecture. The public JSON records exact source commit, version, toolchain, signing status, checksum and resource inventory, with no absolute source/build paths. The DMG is compressed (UDZO), named `tap-n-filter <X.Y.Z[-stage.N]>`, and holds only the app and an `Applications` link; debug symbols are omitted. Both the exact-tag detached source checkout and scratch live in a fresh mode700 temporary root with a generic absolute path, not a user-home checkout. The final App build also remaps source prefixes and disables Swift debug output. This preserves the generated SwiftPM resource fallback without embedding a user-home path. Only that owned worktree and temporary root are removed afterward; no broad Git prune is used. Packaging refuses embedded /Users/ or /home/runner/ paths in the executable. This targeted check does not replace final privacy review.

## Opening an artifact

Open the DMG and drag `tap-n-filter` to Applications; the ad-hoc signature still needs Open Anyway at first launch. With no explicit or packaged data path the app uses `~/Library/Application Support/tap-n-filter/library-v5.json`; it never reads, writes or creates anything in the `com.loganrooks.tap-n-filter` folder by name. Every normal launch first prepares that `tap-n-filter` folder (created mode 0700 if missing, existing folders not chmodded). The launch is refused at startup if the folder is a symlink or not a directory, or if an existing `library-v5.json` there is not a regular file with link count 1; nothing is followed. Before any library or audio work the launch then takes an exclusive non-blocking `flock` on `tap-n-filter/.instance.lock`, whichever library path was selected; a copy that cannot take it, including because the lock file is not a plain single-name file of the user, quits silently. It also quits silently if another running TNF-family process is listed by `NSWorkspace` (bundle ID `com.loganrooks.tap-n-filter` or starting `com.loganrooks.tap-n-filter.`, or executable `tap-n-filter`), which is the only check that covers the working app, since that app does not take the lock. Smoke and probe launches take neither the lock nor the default folder. Before publishing, the build attaches the DMG read-only and hidden at a fresh mountpoint, checks that its root holds only the app, an `Applications` link to `/Applications` and `.fseventsd` metadata, compares the app's complete inventory (every file, dot-files and signature included) with the staged app, and checks the signature and architecture.

After any attach attempt, including one that fails or is interrupted, the build tries a plain detach and then up to two forced detaches, removes the mountpoint only after one succeeds, and refuses if none does. The `NSWorkspace` read is a point-in-time snapshot, and the lock is an advisory lock on one user's folder: neither excludes a copy of the app running as another user or a program that ignores the lock.

## Publishing and reruns

Build jobs have read-only contents permission. Only the separate prerelease job has contents write permission, after both matrix legs pass. Eligible alpha and beta tags create a draft prerelease, upload only the two DMG/provenance pairs, compare returned SHA256 digests and then publish it. It never marks a release latest. Stable tags stop at workflow artifacts. Publishing a stable release remains a separate deliberate owner action.

Concurrency serializes the same tag without canceling an active release. Workflow artifacts are immutable and are never overwritten. A publishing retry finds drafts through the authenticated, paginated release listing, separately from the published-by-tag lookup, and can finish a single exact matching partial draft using the same downloaded bytes. Ambiguous, malformed or incomplete listings refuse before draft creation. Existing release metadata and asset digests must match exactly. Missing digests, unexpected assets, incomplete uploads or different bytes refuse, without deleting/replacing any asset. Rebuilding the same tag may yield different binary bytes; that is a refusal, not permission to replace an earlier release. Prefer rerunning only the failed publishing job with its original retained build artifacts. There is no automatic network retry.

Before any actual tag is pushed, the lead records privacy of source/notes/assets, rollback and version-owned data isolation, and the required local performance disposition. The previous numeric beta target is withdrawn. No replacement numeric budget is ratified. The first beta awaits the operator decision after the required performance measurements. A lead-accepted overnight sound-OFF surrogate can satisfy only that scoped prerelease UI check. It does not establish sound-playing, physical-input or audio-thread performance or listening acceptance. Hosted CI does not manufacture those decisions. A stable release still waits for operator listening and the full release disposition. This workflow cannot enforce a human's decision to push a tag; it enforces tag/source/artifact correspondence after that deliberate action.

## Local checks and current limits

Run `python3 -B -m unittest discover -s tools/release -p 'test_*.py' -v` for bounded synthetic fixtures. Native signing/architecture outcomes and API writes are injected and labelled synthetic. They are not real build/signature/hosted-run evidence. Run `actionlint .github/workflows/release.yml` for workflow syntax. No helper installation is required. Any local compile or heavy check must use the project's private storage guard; hosted CI deliberately has no private guard dependency.

The isolated automation preparation does not fix source SDK compatibility or replace the current CI owner's changes. Merge those through their own review before tagging. An actual hosted tag run, archive launch, native signing result, listening acceptance and final outgoing asset privacy inspection remain pending.
